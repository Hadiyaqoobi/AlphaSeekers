# AlphaSeekers — Deployment Runbook

Operational guide for deploying AlphaSeekers to production on Render + Neon Postgres.
Read this end-to-end before the first production deploy.

---

## 1. Required environment variables

Set these on the Render web service (`alphaseekers`). Values marked **secret** must
be provided manually (they are `sync: false` in `render.yaml`).

| Var | Required | Notes |
| --- | --- | --- |
| `ALPHASEEKERS_MODE` | yes | Set to `production`. Disables demo auth, auto-seed, mock Meet links, DB→memory fallback. |
| `NODE_VERSION` | yes | `20.18.1` (pinned in `render.yaml`). |
| `DATABASE_URL` | yes, secret | **Neon POOLED** string (host contains `-pooler`), `?sslmode=require`. |
| `DATABASE_CONNECTION_LIMIT` | optional | Appended as `?connection_limit=<n>`; small value (e.g. `5`) with the pooler. |
| `NEXTAUTH_URL` | yes, secret | Public origin, e.g. `https://app.alphaseekers.com`. |
| `NEXTAUTH_SECRET` | yes | Auto-generated by Render. |
| `CRON_SECRET` | yes | Auto-generated. Must MATCH on every cron job service. |
| `DATA_ENCRYPTION_KEY` | yes, secret | AES-256-GCM key, base64 32 bytes (see §2). Required in prod. |
| `TELEGRAM_WEBHOOK_SECRET` | if Telegram | Shared secret for the `X-Telegram-Bot-Api-Secret-Token` header. |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` | if Web Push | See §2. |
| `GROQ_API_KEY` | if AI | Primary LLM (console.groq.com). |
| `GEMMA_API_KEY` | if AI | Fallback LLM (aistudio.google.com). Some SDKs use `GOOGLE_GENERATIVE_AI_API_KEY` / `GEMINI_API_KEY`. |
| `HF_API_TOKEN` | if AI | Embeddings (huggingface.co). |
| `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` / `R2_BUCKET` | if uploads | Cloudflare R2 credentials. |
| `R2_PUBLIC_BASE_URL` | if uploads | Public asset URL; also drives the image/CSP allowlist in `next.config.mjs`. |
| `SMTP_USER` / `SMTP_PASS` / `SMTP_FROM` | if email | Transactional email (see §5 — prefer a real ESP, not Gmail). |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GOOGLE_OAUTH_REDIRECT_URI` / `GOOGLE_API_KEY` | if Google OAuth | Google integrations. |

## 2. Generating secrets

- **`DATA_ENCRYPTION_KEY`** (AES-256-GCM master key):
  ```bash
  openssl rand -base64 32
  ```
- **VAPID keys** (Web Push):
  ```bash
  npx web-push generate-vapid-keys
  ```
  Copy the public/private keys; set `VAPID_SUBJECT` to a `mailto:` address.
- **`NEXTAUTH_SECRET` / `CRON_SECRET`**: Render auto-generates these. If setting
  manually: `openssl rand -base64 32`.

## 3. Database & migrations

- Use the **Neon pooled endpoint** for `DATABASE_URL`. See `src/lib/prisma.ts` for why
  (serverless load exhausts the direct endpoint's connection cap).
- Migrations run automatically on every deploy via the build command in `render.yaml`:
  ```
  npm install && npx prisma generate && npx prisma migrate deploy && npm run build
  ```
- `prisma migrate deploy` applies committed migrations only (no schema drift, no prompts).

## 4. Cron jobs on Render

Five scheduled jobs are declared in `render.yaml` as `type: cron` services. Each curls
an app endpoint with the `CRON_SECRET` bearer token. Set `APP_BASE_URL` and `CRON_SECRET`
on each cron service (CRON_SECRET must match the web service).

| Job | Schedule | Endpoint | Method |
| --- | --- | --- | --- |
| reminders | `*/10 * * * *` (every 10 min) | `/api/cron/reminders` | POST |
| scheduler | `0 * * * *` (hourly) | `/api/cron/scheduler` | POST |
| ai-prep | `0 3 * * *` (nightly) | `/api/cron/ai-prep` | GET |
| data-retention | `30 3 * * *` (nightly) | `/api/cron/data-retention` | GET |
| neon-warm | `*/5 * * * *` (every 5 min) | `/api/cron/neon-warm` | GET |

If your Render plan/region does not honor blueprint `cron` services, create them
manually in the dashboard as **Cron Job** services using the schedules/commands above.
The endpoints accept either `Authorization: Bearer $CRON_SECRET` or the
`x-cron-secret: $CRON_SECRET` header.

## 5. Paid-tier sizing (~$70-90/mo floor)

The audit's minimum recommended production footprint:

- **Render Standard web service** (this blueprint) — no cold starts / idle sleep,
  more RAM than free's 512MB. Consider 2 instances for redundancy.
- **A worker** if long-running background processing is added (currently cron covers it).
- **Render cron jobs** (starter) for the five schedules above.
- **Neon paid plan WITH the pooler endpoint** — pooled `DATABASE_URL`.
- **Transactional email provider (ESP)** — e.g. Resend/Postmark/SES — not personal Gmail
  SMTP (rate limits + deliverability).
- **Separate dev and prod databases** — never share one Neon DB across environments.

The `free` tier CANNOT serve this scale: services sleep after ~15 min idle
(30s+ cold starts), cap RAM at 512MB, and cannot scale horizontally.

## 6. Manual pre-launch checklist

- [ ] Set `ALPHASEEKERS_MODE=production` on the web service.
- [ ] Rotate/remove all demo credentials and seeded demo accounts.
- [ ] Provision a **separate** production Neon DB (do not reuse the dev DB).
- [ ] Set `DATABASE_URL` to the pooled endpoint; verify with a connection test.
- [ ] Generate and set `DATA_ENCRYPTION_KEY` (store the value in a password manager —
      losing it makes encrypted data unrecoverable).
- [ ] Generate and set VAPID keys if Web Push is enabled.
- [ ] Set `CRON_SECRET` (matched across web + all cron services).
- [ ] Configure R2 vars and `R2_PUBLIC_BASE_URL`.
- [ ] Switch email from Gmail SMTP to a transactional ESP.
- [ ] Confirm boot logs show no insecure-toggle FATAL error (see `src/lib/runtime.ts`).
- [ ] Verify security headers are present (CSP, HSTS, X-Frame-Options) via `curl -I`.
