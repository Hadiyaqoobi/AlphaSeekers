PART 1: BUSINESS REQUIREMENTS DOCUMENT (BRD)
1. Executive Summary
1.1 Problem Statement
AlphaSeekers is an online learning network providing free education exclusively to Afghan girls in Afghanistan. In a context where girls face severe restrictions on formal education, AlphaSeekers is a lifeline: live, volunteer-taught classes in languages, arts, and professional skills delivered over the internet.

In its first year, AlphaSeekers grew to approximately 500 students across 28 classes using WhatsApp groups and manually-created Google Meet links. Administrators individually schedule classes, create Meet links, and distribute them through WhatsApp. This manual approach is unsustainable as the network scales toward 50 classes in Year 2.

Afghanistan’s internet infrastructure presents unique and critical challenges that must drive every technical decision: connections average 2G–3G speeds (often under 1 Mbps), mobile data is expensive relative to income, power outages are frequent, and virtually all students access the internet through low-end Android phones. The platform must be built specifically for these constraints—not adapted after the fact.

1.2 Proposed Solution
Build an ultra-lightweight, production-level web platform that centralizes class management, auto-schedules classes from teacher availability, generates Google Meet links, and distributes notifications via WhatsApp. The entire infrastructure must run on free-tier services (Vercel, Neon, etc.) to maintain zero hosting cost for this non-profit operation. The platform must deliver a usable experience on 2G connections with total page weights under 200KB.

1.3 Mission
AlphaSeekers exists to empower Afghan girls through education when formal schooling is denied to them. Every technical decision must be evaluated through one lens: does it make education more accessible to a girl in Kabul, Herat, or Mazar-i-Sharif with a slow phone, expensive data, and unreliable power?

1.4 Target Users
	•	Students: Afghan girls (ages 14–25) in Afghanistan seeking free education. Mobile-only, slow internet, limited data plans, low-end Android devices.
	•	Teachers: Volunteer educators (Afghan diaspora and international supporters) who donate their time. Mix of mobile and laptop users with generally better connectivity.
	•	Administrators: AlphaSeekers team members managing operations. Laptop users with moderate connectivity.

1.5 Business Model
Non-profit, 100% free for all users. Funded by volunteer effort. Platform must operate at zero or near-zero cost using free-tier cloud services. No paid subscriptions, no ads, no monetization. Future funding via grants and donations if the platform proves impact.

2.2 Non-Negotiable Technical Constraints
	•	Initial page load must work on 2G: < 200KB total transfer, < 3 seconds on 500Kbps
	•	No client-side JavaScript bundle > 50KB gzipped. Server-render everything possible.
	•	All images must be WebP, compressed, lazy-loaded, with explicit width/height (no layout shift)
	•	API responses must be < 10KB JSON. Paginate aggressively (10 items/page max).
	•	Every form must auto-save state to localStorage. If connection drops mid-submit, data is preserved.
	•	Every API call must have retry logic with exponential backoff (3 retries, 1s/2s/4s delays).
	•	Offline-first class schedule: cache the student’s schedule locally so they can view it without internet.
	•	No web fonts. Use system font stack: -apple-system, Segoe UI, Roboto, sans-serif.
	•	No animations, transitions, or visual effects that consume CPU/GPU on low-end devices.
	•	WhatsApp is the primary notification channel (not email—many students don’t check email).

2.3 Dari/Pashto Language & RTL Support
	•	Platform UI must support RTL (right-to-left) layout for Dari and Pashto speaking users.
	•	Class content may be delivered in various languages, but the platform chrome should be in Dari with English fallback.
	•	Text must render correctly in both RTL and LTR contexts (e.g., English class name inside Dari UI).

5. Four Programs
5.1 Online Classes (Core — MVP)
The heart of AlphaSeekers. Live classes delivered via Google Meet, managed through the platform. Currently 28 classes across 13 subjects scaling to 50 in Year 2.

Current subjects (2025): English, Korean, Chinese, Spanish, Arabic, German, Anatomy, Journalism, Writing, Painting, Public Speaking, Handwriting, Photoshop.

Classes are delivered via Google Meet and coordinated through WhatsApp. The platform replaces the manual coordination while keeping Meet and WhatsApp as the actual delivery and communication channels that students already know.

5.2 Informative Webinars
Drop-in events on career development, mental health, technology. No enrollment or progress tracking—lighter than classes. Registration + Meet link distribution only.

5.3 Sharing Opportunities
Curated feed of scholarships, internships, and grants relevant to Afghan girls. Admin-posted, student-browsable with filters by type and deadline.

5.4 Library & Reading Books
Digital library of free reading materials, e-books, and educational resources. Stored on Cloudflare R2 (free, fast CDN). Searchable by subject and category. Must support PDF downloads for offline reading.


6. Future Plans (Post-MVP)
6.1 Visual Python Learning Application
A structured Visual Python curriculum as a scholarship and teamwork program for girls. The approach is intentionally phased: the founder and a friend will first learn the curriculum themselves, documenting the process—time required per day, learning curve, experiences. Only after completing the curriculum and understanding the journey will they design a stable program for other girls. The team will then collaborate on building projects and potentially providing online job opportunities. This is the key long-term differentiator alongside classes.

6.2 Offline Classes
In preparation. AlphaSeekers has strong access to teachers and students for in-person delivery. Team structure and systems are being planned (may take several months). The platform should be designed to eventually support offline class management but this is not in MVP scope.

6.3 Website Articles
Blog/article section for educational content, student success stories, and community news. Post-MVP feature.

3. Epics & User Stories
Epic 1: Class Discovery & Enrollment
US-01: Browse Class Catalog
Priority: P0
Epic: Class Discovery
Sessions: 2 sessions

As an Afghan girl student, I want to browse available classes on my phone even on slow internet, so that I can find classes to learn new skills.

Happy Path:
	•	GIVEN I visit the AlphaSeekers platform on my Android phone (2G/3G)
	•	WHEN the Classes page loads
	•	THEN I see class cards organized by category (Languages, Arts, Professional Skills)
	•	AND each card shows: title, teacher name, schedule, language, enrolled count
	•	AND the TOTAL page transfer is < 150KB (HTML + minimal CSS + data)
	•	AND the page renders in < 3 seconds on a 500Kbps connection
	•	AND the layout is RTL-compatible for Dari/Pashto UI

Failure / Edge Path:
	•	WHEN API fails or times out: Show cached class list from localStorage (if previously loaded) with a ‘Retry’ button and ‘Last updated: [time]’ indicator
	•	WHEN connection drops mid-load: Partial content renders with skeleton placeholders; auto-retries 3x with exponential backoff
	•	WHEN no classes exist: Friendly message in Dari and English

Edge Cases:
	•	What if student has only 2G? Server-side rendered HTML with zero client JS for initial view; progressive enhancement only
	•	What if 50+ classes? Server-side pagination (10/page); no infinite scroll (saves data)

Acceptance Criteria:
	•	Page loads < 3 seconds on simulated 500Kbps (Chrome DevTools throttle test)
	•	Total transfer < 150KB verified in Network tab
	•	Classes display correctly in RTL mode
	•	Cached fallback works when server is unreachable
	•	Pagination works and loads next page < 2 seconds
Proof Method: Chrome DevTools Network throttle test at 500Kbps; verify transfer size; test RTL layout; disconnect network and verify cached fallback

US-02: Student Enrollment
Priority: P0
Epic: Class Discovery
Sessions: 2 sessions

As a student, I want to enroll in a class with one tap, so that I receive the Meet link and class schedule on WhatsApp.

Happy Path:
	•	GIVEN I am logged in and viewing a class detail page
	•	WHEN I tap ‘Enroll’
	•	THEN I see immediate optimistic UI (‘Enrolled!’ with checkmark) while the API call completes in the background
	•	AND within 2 minutes I receive a WhatsApp message with: class schedule, next session date/time, and Meet link
	•	AND the class appears in my ‘My Classes’ tab

Failure / Edge Path:
	•	WHEN API call fails: Optimistic UI reverts; ‘Enrollment failed—tap to retry’ appears; form data preserved
	•	WHEN WhatsApp delivery fails: Fallback to in-platform notification + email
	•	WHEN connection drops during enrollment: Request queued in localStorage; auto-retries when connection returns

Edge Cases:
	•	What if student double-taps? Enrollment is idempotent; server rejects duplicate
	•	What if student wants to unenroll? Unenroll option in ‘My Classes’

Acceptance Criteria:
	•	Enrollment completes (student in roster) verified via API
	•	WhatsApp notification delivered within 2 minutes
	•	Optimistic UI shows instantly even on slow connection
	•	Offline enrollment queued and processed on reconnect
Proof Method: Tap enroll on throttled connection; verify optimistic UI; verify API roster update; verify WhatsApp delivery log

US-04: Auto-Schedule Classes with Google Meet
Priority: P0
Epic: Scheduling
Sessions: 5 sessions

As an admin, I want the system to auto-generate class schedules and Meet links from teacher availability, so that I stop spending hours on manual coordination.

Happy Path:
	•	GIVEN a teacher has set availability and is assigned to a class
	•	WHEN the auto-scheduler runs (Vercel Cron job, daily at midnight UTC)
	•	THEN the system creates class sessions for the upcoming week
	•	AND generates Google Meet links via Calendar API
	•	AND stores schedule + links in the database
	•	AND triggers WhatsApp notifications to enrolled students

Failure / Edge Path:
	•	WHEN Google Meet API fails: Sessions created without links; admin alerted to add manually; retried next cron run
	•	WHEN Vercel Cron times out (10s limit): Scheduler processes classes in batches across multiple cron invocations (10 classes per run, every 5 min until done)
	•	WHEN teacher double-booked: System prevents overlap; alerts admin
	•	WHEN Neon DB is cold: First cron invocation warms the DB; actual scheduling on second invocation

Edge Cases:
	•	What if class has no students yet? Schedule created anyway (ready when students enroll)
	•	50 classes won’t process in one 10s function? Batch processing across multiple cron calls

Acceptance Criteria:
	•	Sessions appear in admin dashboard with Meet links
	•	Meet links are valid (verified by opening in browser)
	•	Students receive WhatsApp with correct schedule and link
	•	No teacher double-booking
	•	Scheduler completes 50 classes within 30 minutes (across batched cron runs)
	•	Entire scheduling pipeline stays within Vercel 10s function timeout per invocation
Proof Method: Trigger scheduler; verify Meet links in DB; verify WhatsApp logs; test with 50 classes across batched cron runs

As an admin, I want to add books and resources to the digital library stored on free cloud storage, so that students can download and read offline.

Happy Path:
	•	GIVEN I am logged in as admin
	•	WHEN I add a resource (title, author, category, file upload to Cloudflare R2 or external URL)
	•	THEN it is published and searchable in the student library
	•	AND PDFs are served via R2 CDN for fast, free downloads

Failure / Edge Path:
	•	WHEN upload fails: Error + retry; metadata preserved
	•	WHEN R2 is unreachable: Fallback to direct URL if provided

Acceptance Criteria:
	•	Resources appear with correct metadata
	•	Students can search by title, author, subject
	•	PDFs download from R2 CDN (verify headers)
	•	File upload limited to 5MB with validation
Proof Method: Upload resource; student searches and downloads; verify R2 CDN delivery

4.2 Security
	•	Authentication: Email + password with JWT tokens (via NextAuth.js); role-based access (student, teacher, admin)
	•	All traffic over HTTPS (Cloudflare handles SSL termination)
	•	API routes protected by role middleware; students cannot access admin/teacher endpoints
	•	No personal data (phone numbers, full names) exposed in public API responses
	•	WhatsApp numbers stored encrypted; only used for notification delivery
	•	Rate limiting on auth endpoints (prevent brute force)

4.3 Reliability & Resilience
	•	Uptime target: 99% (Vercel has 99.99% SLA even on free tier)
	•	Database: Neon handles backups automatically; 7-day point-in-time recovery on free tier
	•	Graceful degradation: If Google Meet API fails, platform still works for browsing, enrollment, and materials
	•	Retry logic on ALL external API calls (3 retries, exponential backoff: 1s, 2s, 4s)
	•	Circuit breaker pattern: After 5 consecutive failures, stop calling failing service for 5 minutes
	•	Notification chain: WhatsApp → Email → In-platform banner (never silently fail)

4.4 Accessibility & Mobile
	•	Mobile-first responsive design (tested on 360px width—common low-end Android screen)
	•	RTL layout support for Dari and Pashto (CSS logical properties: margin-inline-start, etc.)
	•	System font stack only: -apple-system, Segoe UI, Roboto, sans-serif (zero font downloads)
	•	Minimum touch target size: 44x44px (per WCAG guidelines)
	•	No animations, transitions, or hover-dependent interactions
	•	Color contrast meets WCAG AA (4.5:1 minimum for text)
	•	Works on Android 10+ with Chrome (the dominant browser in Afghanistan)
	•	Progressive Web App (PWA) manifest for add-to-home-screen on Android

4.5 Internationalization (i18n)
	•	Default UI language: Dari (with English fallback)
	•	All user-facing strings externalized for translation (next-intl or similar lightweight i18n)
	•	RTL/LTR layout switches automatically based on language
	•	Date/time displayed in user’s timezone (stored UTC in database)
	•	Class names and descriptions may be in any language (mixed-direction text handled)

5.2 Architecture Principles
	•	Server-first: Render HTML on the server. Client JS only for interactivity (enrollment, forms, schedule cache).
	•	Progressive enhancement: Every page must work with JS disabled (core reading/browsing). JS enhances with optimistic UI, caching.
	•	Edge caching: Public pages (class catalog, opportunities, library) cached at Cloudflare edge. Reduces Vercel function invocations.
	•	Offline-capable: Service worker caches student schedule + class materials list. Full offline reading of downloaded PDFs.
	•	API minimalism: Every API route returns only the fields the client needs. No ‘select *’. No nested objects unless necessary.
	•	Batched operations: Auto-scheduler processes 10 classes per cron invocation to stay within 10s timeout. Runs every 5 min until complete.
